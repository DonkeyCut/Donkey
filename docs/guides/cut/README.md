# Donkey Cut

Donkey Cut is a free video editor that runs in the browser; code and paths shorten the name to `cut`. Its product domain is `donkeycut.com` — a marketing landing at `/` and the editor at `/app/…`; links on retired domains are redirected there at the edge (Cloudflare). The host serves only the client bundle — every page is client-rendered — and using the editor requires a Donkey sign-in.

A project lives in one of three homes, chosen when it is created. A browser project keeps its files in the page's own origin-private storage, so a fully local project needs nothing installed. A project on a Mac talks to the Donkey Cut engine — a local server the Donkey Mac app ships and supervises, which uses local disk, the app's bundled ffmpeg, on-device speech, and the user's own Claude/Codex CLI logins; the engine's projects and library belong to the Mac user, shared by every Donkey account that signs in on that Mac. A cloud project stores its doc and media on Donkey's hosted servers. The user chooses between the two places they think in — Local and Cloud — and which store backs Local is the session's business: the Mac's engine once the app has connected, the browser's own storage otherwise.

AI generation — images, video, and voiceovers — and the assistant's Gemini models spend credits: whatever the project's home, the page posts to Donkey's hosted inference routes with the user's session and credits. `donkeycut.com` owns sign-in directly — the auth pages and the Google callback serve on that host — so the session is a plain host-only cookie. Generated media lands back in the project like any other file; Gemini chat turns, including their editor tool calls, run entirely in the page.

**The engine rule:** the engine API surface (`/api/cut/*`) runs only on the user's Mac. On a hosted deploy every one of those routes answers 404 before any handler runs, so the unauthenticated routes are unreachable there and nothing can execute off-Mac — the engine has no path to Donkey's production models; the page reaches them only through Donkey's own authenticated inference APIs. Don't wrap the engine's routes in the Donkey auth helper, reach for Prisma from them, or bill them against credits; local-only is the design for everything the engine does.

The cloud adds a second surface with the opposite rules on purpose: `/api/cut-cloud/*` is the engine's hosted twin — the same route shapes, but session-authenticated, storing docs in Postgres and media in R2, and metering model calls through credits. Browser projects answer their storage routes in the page itself, out of origin-private storage, and ride the hosted twin for AI, metered like cloud projects. A project lives in exactly one home, and the client picks the surface per project; the surfaces never proxy to each other. See [Cloud projects](#cloud-projects).

## How it works

The page comes from wherever is convenient — the hosted domain, or one local dev server that serves pages and APIs from the same origin — and the work happens where the project lives.

```
browser (the editor)
  ├─ browser project ─▶ origin-private storage in this browser
  │                     (AI rides the hosted twin)
  ├─ cloud project ───▶ /api/cut-cloud/* · Postgres · R2
  └─ local project ───▶ the engine on 127.0.0.1 (spawned by the Donkey app)
                          local disk · bundled ffmpeg · on-device speech
                          · the user's own claude/codex CLI logins
```

**What loads is cached locally.** Every visit re-reads the same three things: the projects listing, the library, and a project's document. The browser keeps the last answer to each in IndexedDB, scoped to the account and the backend that served it, and paints it on arrival while the real request runs behind it. So returning to a project draws on the next frame instead of after a round trip, and a project you just created opens on a document the client already knows is empty. A snapshot is a head start and the live answer always replaces it; where the two disagree the server wins. The one exception is an edit made on top of a snapshot — that is kept rather than overwritten, saves like any other edit, and a cloud project whose stored copy really has moved on answers that save with the version conflict it already had.

The client probes the engine's health endpoint (dedicated port first, dev server second) and remembers the winner. Browsers permission-gate a hosted page's calls to the local machine, so the page probes only when that raises no prompt — it is served by the engine, or the permission is already granted — and starts in the cloud otherwise. The engine grants the hosted origin cross-origin access, and only that origin. Nothing walls the app, because cloud editing always works. Closing the Donkey app does not hide the work made in it either: a browser that has reached this Mac's engine before keeps listing that shelf from the listing it stored, so those projects stay on the home beside the cloud ones, each badged with where it lives. They are read-only while the app is away — no renames, moves, or deletes — and opening one says that it lives on this Mac rather than guessing at a cloud copy that was never there. That is where the warning belongs, so that is the only place it appears: a banner over the thing that will not open, which the user cannot dismiss and which opens the recovery steps in a dialog with the button that fires the browser's permission prompt. Probing continues behind it, so starting the app clears the banner and loads the project. Engine updates ride the Donkey app's own auto-updater, so the client never prompts to update.

**A cut needs no footage.** The frame starts as a color the project owns, and everything else — clips, titles, shapes, stickers — draws over it. So a video made entirely of text and graphics is an ordinary project: it plays, exports, shares, and renders on the worker like any other, and the same color letterboxes a fitted clip and fills a gap on track 0. Elements stack by row: two on one row slide clear of each other in time, so a title that sits over a card lives a row above it.

**Framing is per clip.** Every video clip meets its box — the whole frame, or the region it was given — through one geometry: fitted with margins or covering with a crop, zoomed in further, panned to choose what the crop keeps, turned, faded, cornered, masked, and shadowed. One function computes where the picture lands, the preview draws that rectangle, and the export graph scales and crops to the same numbers, so a reframed clip looks the same on every surface, freeze frames and headless renders included. On the stage the selected clip wears two outlines: a blue box for its layout, with grips to move, resize, and rotate it, and a grey dashed one standing where the source really lands, so the part a crop discards stays visible — its corners zoom the picture and its interior pans it. The shadow is cast by the shape the clip actually shows, mask included, which is what makes a circle-masked camera bubble throw a circular shadow.

**Words as the picture.** A lyric video, a kinetic-typography passage, a quote sequence: the assistant places a whole run of lines in one call, carrying a named look. A look is the design of the whole run rather than of one line — the frame color, the cards it cycles, and the ensemble the run walks across its length: the faces it rotates through, the entrances, where successive lines land in the frame, and what each line does while it holds. That is what stops a hundred lines coming out identical and dead center, which is the failure a text video actually has. The looks live in one registry the tools and the skills both read, so adding a look teaches the assistant a new style with no other change. Words ride one of two carriers — a caption track, which holds per-word timings and can light each word as it is sung, or elements, which give each line its own card, color and motion. Text the user already has (lyrics, a script) is timed by aligning it to a transcript of the audio: the recognizer supplies the clock and the user's wording is kept exactly, which is what makes it survive singing.

**Motion is data.** Every animation in the editor — an entrance, an exit, a loop, and the moves an element makes while it holds — is one format: a pose keyframed over a normalized window with cubic-bezier easing, plus a range selector that says how the motion is handed from one character to the next. That is the After Effects text-animator model, the one Lottie serializes, and picking it means a preset and a hand-keyed track are the same object at two levels of convenience: the named entrances, loops, and moves are slots on the element, evaluated internally, and anything no name covers is keyed directly on the element's own pose track — the track stays whatever the user keys by hand. The library is a JSON asset in the effects kit rather than code, and the menus, tool enums, prompts, and the frame sampler's crop budget are all read from it, so adding an animation is adding an entry. One evaluator samples it, which is what keeps the preview, the export, and the headless worker showing the same motion. A slot may also carry a preset of its own rather than naming one from the library, in the same shape a library entry has — the evaluator cannot tell the two apart, so an animation composed inside a project plays wherever a shipped one does.

## The preview

The preview decodes the cut itself. Every clip on screen owns a decoder reading its file directly — the container is parsed in the page and frames come off WebCodecs — and a small ring of already-decoded frames sits beside it. Drawing a frame is a question answered from that ring, never a wait: playing walks each file forward and keeps the ring ahead of the playhead, scrubbing asks for one moment and the newest ask wins, and if the exact frame has not landed the nearest one already decoded goes up and is replaced when the real one arrives. A held frame is worth more than a stall.

Decoders live in a bounded pool, and leaving the pool is suspension before it is closure: an idle source gives up its decoder but keeps the parsed file and the canvases its frames land on, so the next visit wakes it for the cost of one keyframe seek. The canvases are the part that must not churn — a montage of short clips replayed for a few minutes, allocating a fresh set on every reopen, floods the GPU process until frames stop arriving at all. They also must not pile up, so the warm shelf of stood-down sources is capped by the memory it holds rather than by a count of them: a small stage keeps a montage's whole cast, a large one keeps a few, and what does not fit closes for real.

Two things follow from that. A cut is a read from a different ring rather than a handover between players, so crossing a join costs nothing and needs no clock to change hands; and the picture answers a moved playhead inside a frame, because the answer was already in memory. Sound is scheduled on one audio context, a window at a time, and its clock is what playback runs on — the picture follows the sound rather than the two chasing each other. When a browser holds that context suspended, as it does until the page has been interacted with, wall time carries the cut and the audio clock is picked up once it agrees — and when the clock jumps instead of agreeing, a context resumed late or an output device switched mid-play, every scheduled window restarts where the clock now stands rather than playing out the moment it was placed for.

What is on screen at a given instant is still a pure function of the document and a time, and it is still the same function an export asks. The preview reaches an instant by playing toward it and an export by jumping straight there; because both draw through one compositor from one plan, the file cannot quietly disagree with what was watched.

The stage sits under a camera. The picture opens fitted to its pane, and that fit is 100%: from there a pinch or ⌘-scroll zooms about the cursor, a plain scroll pans, and a drag on the empty room around the picture — or a middle-button drag anywhere — moves the view. The camera holds its place on screen when a panel opens or the selection changes shape; the pan absorbs the layout's move, so the picture stays where the eye left it. A round control in the pane's top-right corner appears while the camera moves and lingers a moment after, opening into the zoom level, a step in each direction, and a Reset that refits.

The playhead lives apart from the document. It moves sixty times a second and the document does not, so a moved playhead wakes the surfaces that draw it and nothing else — and a paused editor with nothing changing schedules no frames at all.

Whether any of this is true of a given build is measured rather than assumed: `npm run eval:cut-perf` drives a real editor in a real browser against fixture montages and reports how long the picture takes to answer a moved playhead, whether any frame crossing a cut was the wrong one, and whether a fast-cut montage replayed for minutes still holds the picture to the clock the way its first pass did. Its committed report is the baseline a change is diffed against.

The machine it measures on is part of the measurement. A developer desktop has decode slots to spare and never falls behind, so the preview's caps never bind there and a change that would ruin a laptop reads as a clean sheet. `--machine` puts the page on a smaller one: it takes away hardware decode slots, so decoders past the limit deliver their frames late the way software decoding does, and it slows the main thread to a fraction of this one. `npm run eval:cut-perf-lowend` is the profile the reports come from. What the gates ask there is what a viewer would ask — did the frames arrive, did the picture hitch a quarter second behind the sound, and was the last pass as good as the first — and each machine has its own budget for those, because a number that is honest on a desktop is fantasy on a fifteen-watt laptop.

A profile it cannot model is the one someone is actually editing on, so the preview can report on itself. Settings carries a diagnostics switch, off until an account turns it on; with it on, the engine counts what its played frames did — how many arrived late, how far the picture sat behind its own sound, what the decoders and the warm shelf were holding, how long the main thread was blocked — and sends one summary per half minute of playback, alongside what the machine brought: cores, memory, the size it is decoding at, and which codecs it decodes in hardware. That last one separates the two stutters that look identical from outside: a machine spending its time after the decoder, and one whose decoder refused the footage and put every stream on the CPU. The summaries are numbers; no frame, no sound, and nothing naming the project leaves the browser.

## Color grading

A clip's color is one field on the clip: an optional preset underneath and manual adjustments on top — sliders, tone curves, color wheels, per-hue bands. Every part is absent when neutral, so an untouched clip carries nothing, and the preset's intensity scales its parameters toward neutral so half-strength means half the move, never a crossfade through gray.

Presets are JSON documents beside the effects kit, one file per category, and the kit's parser is the only doorway that data has into the engine — the shipped catalog loads through the same validation a user-imported or shared grade will use later. Every shipped recipe is an original design on this model.

Every preset is measured, not eyeballed, in two tiers. The first is safety, held to the references a colorist grades against: the ColorChecker chart pushed through each preset's real lookup table, skin kept on the vectorscope's skin-tone line and under a saturation ceiling, the gray ramp monotonic, shadow detail preserved, and any white-balance cast kept inside warming-gel range.

The second tier is identity. Every preset names something real — a film stock, a lab process, a lighting condition — and has to measure like the thing it names, so each one declares its referent alongside the signature that referent leaves on a chart. A bleach bypass has to actually drain color while contrast climbs; an expired stock has to show the crossover uneven dye decay produces; a sepia has to collapse the frame onto one tone rather than tinting surviving color. Presets also have to differ from each other: two recipes that land on the chart together are one look wearing two names, which is how a pair of near-duplicates can otherwise sit on the shelf unnoticed. Both tiers walk the catalog itself, so a preset added to the JSON must declare what it is and is held to the same standard without being registered anywhere.

Skin protection is one rule rather than a habit each stage has to keep. A preset marked to protect skin applies its tone in full and then blends the color it moved back toward the pixel's own, scaled to wherever the tone landed — so hue and saturation survive while brightness follows the grade. Because the rule sits at the end of a layer, a stage added later cannot leak color onto faces by forgetting to damp itself.

One transform renders everywhere. Grades that stay within the original scalar sliders keep the long-standing cheap path — a CSS filter string in the canvas and a lutrgb/hue chain in ffmpeg, derived from the same numbers — and saved grades from before the extension render byte-for-byte as they always did. Anything richer compiles to a single 3D lookup table sampled from one pure function: ffmpeg applies it as a .cube file through lut3d, the browser preview applies it in a WebGL pass, and a headless export applies it on the CPU, all three interpolating the same way. The timeline filmstrip alone approximates, carrying the scalar part of the grade as CSS and stating so in code; the preview and every export render the whole grade.

The assistant grades through the same model: tools for presets, sliders, curves, wheels and hue bands, a stats reader so it grades from measured numbers, and a matcher that computes a grade carrying one shot onto a reference image or neighboring clip by quantile-mapping the channels into curves.

## Cloud projects

Cloud projects follow the account: the same project opens in any browser on any OS. They run alongside local ones — every account has both halves, and which home a project uses is decided per project.

Every client call goes through a backend seam (`site/src/cut/lib/backend/`): the local driver is the engine transport unchanged, the cloud driver rewrites the same paths to `/api/cut-cloud/*` with the session cookie, and the browser driver answers storage routes in the page from origin-private storage, falling through to the cloud twin for AI. Residency is per project and fixed when the project is created, so creating one is where the user chooses. One picker makes that choice, standing beside New project in the sidebar: it names a shelf — Local or Cloud — and everything the browser creates lands there, new projects and anything added to the library alike. Local is this Mac's engine when the app has connected and this browser's own storage otherwise, so a machine without the app still has a real local shelf. The choice sticks on that browser until they change it, and every other New project button follows it. Inside a folder the folder decides, since a project files only into a folder beside it. The home lists every shelf as one listing — the Mac's from its stored listing when the app is closed — each project badged with where it lives, and opening one binds the editor to that project's backend. Capability flags on the driver hide what a backend can't do, so components never feature-detect.

The library is the exception, because it is the user's one shelf across places: every residency keeps a library, and the Library lists them at once as one listing, newest first, with a badge saying which shelf each item is on. So a cloud project can pull a clip off this Mac, and a browser project can pull one out of the cloud. A shelf that lives in the page holds its media in the same origin-private storage its projects use, and a link imported onto it rides the cloud worker — a page can't fetch a video off a YouTube link — with the bytes coming back down and the staged cloud copy dropped after. The Mac's shelf takes that same route as a second try: sites refuse fetches on the strength of the tool making them, so a link the engine's own tools can't bring back is fetched by the worker and lands here anyway. Each shelf is remembered on its own, so the Library tab keeps listing the Mac's items with the app closed, read-only, and clicking one raises the same banner an unreachable local project does. The editor's library picker asks only for what it can reach, since an item it cannot copy into the project has no business in a picker. Each item's own shelf answers for it: previews, renames, and deletes go to the backend it came from, and folders belong to one shelf, so items file only into folders beside them. Adding to a project is the one crossing: on the project's own shelf the server copies the file without the bytes leaving it, and off it the browser carries them down and back up. Filing an item into a folder on another shelf crosses the same way — the bytes come down and go back up, a file with its cover and a template with its own media, and the copy left behind comes off.

The phone feeds the cloud shelf. Clips recorded in the iOS app upload themselves to it, marked as camera footage; that marker gives the desktop its Camera Roll — a tab of phone clips kept out of the main Library grid, and a locked Camera Roll folder in the editor's library panel so the footage drops into any project. Inspiration saved on the phone lands in an Inspiration folder on the same shelf, links riding the same worker import every shelf uses. Notes are the one thing that flows both ways: the phone and the desktop's Notes tab edit the same set, the newer edit winning, deletes carrying across. Notes file into folders of their own, on the shelf's folder table: the desktop files them by dragging onto the same folder tiles the Library uses, the phone by a folder list it opens like any other, and a folder made on either side is on the other by the next pass. Every request from the app carries a client marker, the server remembers accounts it has seen it from, and only those accounts get the phone tabs — a desktop-only account's sidebar never changes. The app's own guide covers the phone side: [The iOS App](../ios-app.md).

Some of what the Library holds is lent. Most items are copied when they are used — a clip's bytes become the project's own — but a font is pointed at: every title set in it names it, and the file stays on the shelf where every project can reach it. Lent items follow three rules. They are identified by their bytes, so the same file on two shelves is one entry in the menu and one id in a document. A new one lands on the shelf every surface can read, whenever it is small and the account has room. And a project moving to the cloud takes what it points at with it, so a title keeps its typeface when it starts rendering there — since the id is the bytes, not a word of the document changes. Fonts are the first of these; a .ttf, .otf, .woff or .woff2 dropped on the Library is filed in folders, deleted, and counted against storage like anything else, and every project offers it for titles and captions. A font download arrives as a zip, so the zip is droppable: the faces come out of it and the licence text stays behind, and a family of eighteen weights becomes a single entry. The file is checked by installing it through the renderer's font seam before any bytes move, so what lands is what a preview and an export can draw with, and the family name comes off the font's own metadata. That same moment draws the specimen the shelf keeps as the file's cover, so a font card shows the alphabet in its own face whether or not the page looking at it has that face installed. A new account starts with an empty Fonts folder to say the shelf takes them; it is an ordinary folder and can be deleted. A render job reaches the cloud shelf alone, which is what those rules are for. A font filed into a folder belongs to that folder's shelf like anything else, and a full account keeps its font on the shelf it was working from: it draws in the tab, is marked in the font menu as living on this device, and falls back to the base face in a render job. A title set in a font that is later deleted falls back too, so nothing in a document has to be rewritten.

Cloud projects store their doc in Postgres (versioned; a stale autosave 409s and the editor reloads the newer copy) and media in R2: uploads go direct from the browser on presigned URLs (the hosted functions never see the bytes), playback streams on signed range URLs, and a flat per-user quota is enforced at presign time. That quota is visible rather than implicit: a free account editing a cloud project sees what it has used in the editor's top bar, and a presign rejected for space opens an upgrade offer wherever it happened instead of a bare error. The same slot carries the countdown when a subscription is set to cancel, and clicking it opens the billing portal.

A dropped file does not wait for that upload. Because a presign claims the stored name before any bytes move, and the browser can read the file it was handed, an import is measured, named, and placed on the timeline in the same moment it is dropped — playing from the local copy, filmstrip and all — while the bytes go out behind the editor. When this browser can hold a store, the dropped bytes are written into origin-private storage under the claimed name and pinned: the document references the asset at once, a tab closed mid-upload resumes the upload on the next open, and once the cloud confirms the object the pin clears and the local file becomes a read cache. A tab-scoped import — a browser with no store — keeps itself honest through the saved document instead: the import stays out of it, along with the clips that use it, until the upload lands, so a tab closed mid-upload leaves nothing to reopen broken. Export waits on the same line, since a render reads the saved document.

The cache runs the other way too: opening a cloud project pulls in the assets this browser is missing, nearest timeline use first. Video caches as fixed-size chunks keyed to the stored object: playback serves the pieces it holds from disk and fetches the rest as byte ranges, so scrubbing warms the exact regions being worked, a half-fetched file keeps every chunk that landed, and the cache carries across the hourly re-signing of media links. Images and audio stream in whole and swap onto local bytes as they land. When the origin's storage quota runs short, chunked video goes first — a lost chunk costs one ranged re-fetch — then the least recently opened projects' whole-file caches; pinned uploads and browser-resident projects are never evicted.

Storage a subscription paid for outlives the subscription for a while: when Pro ends and the account still holds more than the free tier, it keeps everything for thirty days, warned in the editor and on the projects home. After that the daily sweep brings it back under the cap — least-recently-updated projects first, then the oldest library assets, stopping the moment it fits — so what survives is the recent work, and an account already under the cap is never touched.

A cloud project can be shared read-only, Google-Docs style: the editor's Share dialog invites specific emails (viewers sign in) or opens the link to anyone (no sign-in), and switches opt extra surfaces in — chat, media, AI generations, subtitles, details — on top of the always-shared preview and timeline. The share row's id is the link token, so revoking deletes the link. Viewers ride a third backend driver against `/api/cut-shared/<token>/*`, a deliberately public API surface (the one exception to session auth on the cloud side): the server resolves access per request, filters the doc to the shared surfaces before it leaves, and refuses media outside that filter, so hiding is enforced by the backend rather than the client. A public share's reads are cached at the edge for a lifetime that tracks how long the owner has been idle — a doc saved seconds ago is served near-live, one untouched for an hour is served from cache for minutes — and the same number is handed back as the viewer's poll interval, so a link a crowd opens costs a handful of origin requests rather than one per viewer per tick. A restricted share's reads depend on the viewer's session, so they are never cached. A shared project's media is served from Cloudflare's edge rather than presigned against R2's S3 endpoint, which nothing caches: a Worker holding a private bucket binding checks a short token the hosted API mints, then answers from cache keyed on the object alone. Dropping the token from the cache key is what makes the token affordable to keep short — every viewer and every re-mint share one cached copy — and a short token is what makes unsharing mean something, since a presigned URL is a bearer credential nothing can withdraw before it expires. Owner-side editing still presigns R2 directly, where the URLs are minted on fixed windows so a browser can reuse bytes across reloads. A shared link unfurls with the project's own card: the render worker derives a first-frame still and a five-second animation from the opening of the cut, the page's metadata points at them through a URL carrying the doc version, and a project with no card yet gets a drawn one. Viewers poll the doc version on an interval the server picks — shared views trail live edits, they don't stream them — and a "Copy project" action duplicates everything the share exposes — the filtered doc, its media, and the chat threads when chat is shared — server-side into the viewer's own account and quota. Copies queue rather than run in the request: each request writes a job row and publishes it to a Cloudflare Queue whose serial consumer executes one copy at a time, so a burst of copy requests can't stampede storage; the client polls the job for the outcome. An owner duplicating their own cloud project from the dashboard rides the same queue. A cloud project's export renders in the browser. The tab already draws the whole cut for the preview, so it can draw it again frame by frame into an MP4 and upload the finished file — no round trip that pulls the media back out of storage into a container, no waiting behind someone else's render, and a file that matches the preview because the same compositor drew both. A browser that can't carry the render — no scratch storage, no encoder at the requested frame size — sends it to the worker, and so does everything the editor renders on its own behalf: hover-preview proxies, share cards, streaming ladders, and URL imports. That worker is a pool of containers (`site/src/cut/worker/`) that claim job rows from Postgres, reuse the engine's exact ffmpeg pipeline against R2, and report progress back through the rows the client polls. Each replica takes one job at a time, so a render has the whole machine to itself, and the queue is claimed by what someone is watching first: an export or a URL import goes ahead of the background artwork. The artwork waits for a lull too — a project's hover proxy and share card rebuild when the editor closes or the tab goes to the background, so a session of editing spends the pool on the renders the user asked for. Transcription and mic dictation prefer this Mac: with the app running they use on-device speech even for a cloud project, and fall back to a hosted, credit-metered route — Gemini producing cue-level timestamps from browser-rendered audio, word timings interpolated inside each cue — when it isn't. That split between where a project's data lives and where its work runs is its own guide: [Local compute](local-compute.md). The assistant offers its Gemini models (which already run entirely in the page); the Claude/Codex CLI providers stay app-only because they are the user's local logins.

A share link opened on a phone plays rather than edits. The editor composites a project live — a video decoder per clip, painted onto a canvas — which is the right design on a desktop and an impossible one on a phone, where the decoders alone exhaust what a tab is given. So below the width the editor needs, the share serves a player instead: the cut as a single adaptive stream with the platform's own controls, and whichever surfaces the share opted in — chat, media, subtitles, details — as sheets that rise over it. The desktop share is untouched. The choice is made in code rather than in styling, because hiding the editor with a class would still have mounted it and started every decode.

That stream is an adaptive ladder the render worker builds and stores in R2 beside the project's media. A single flattened file is the wrong answer once a cut can run long or land in 4K, for two reasons. The edge declines to cache any object past half a gigabyte, so the file that most needs caching is exactly the one that never gets it, while segments of a few megabytes always do. And one bitrate cannot serve both a phone on a weak cellular link and a desktop on a 4K panel; a ladder lets the player choose, and change its mind mid-watch. Rungs are capped at the source so nothing is upscaled, and the low ones publish first, which is what makes a share watchable well before the slowest rung finishes. Each render writes a new version of the tree, so a viewer already watching keeps playing off the old one while the next is built, and the superseded version is swept a day later. Access is the same short-token scheme as the rest of a share's media, with one difference: the token covers the whole tree and rides in the path, because a player reaches segments by following relative links out of a playlist and a query string does not survive that hop.

A ladder is the one thing in the bucket that is neither the user's media nor charged to them. It is a delivery format the product picked, rebuilt whenever a shared project settles, and the footage it was built from is already paid for — so it carries no media rows and never counts against a storage quota. That is also why it needs an index of its own: with no rows, a tree nothing points at is a leak nothing can find. So a Workers KV record, not the database, tracks every version a project has ever *started* — claimed before the first byte uploads, so a render that dies partway still leaves a trail — along with the one it serves and the ones it has replaced, each stamped with when it was replaced. The sweep runs off those stamps: a replaced ladder gets a day before its segments go, counted from the moment it stopped being current rather than from whenever its bytes were written, and a claim whose render never finished is collected once it is too old to still be running. Work scales with the garbage rather than the project count, so no project waits behind a fixed number of others.

Rebuilding waits for the same lull the hover proxy does — the editor closing, or the tab going to the background — because unlike the five-second card it re-encodes the whole cut once per rung, and an interaction like opening a dialog is the wrong thing to hang that on. At most one ladder renders while one waits, and the waiting one is replaced rather than kept, so an edit made mid-render is never the thing that gets dropped.

What a viewer sees is answered in their favour: until a ladder exists, and while one is still rendering, the phone plays the project's flattened proxy and swaps in the real stream when it appears — though never mid-playback, since replacing a video someone is watching would restart the cut at zero. So a link shared before any of this existed still plays.

Both renders are subject to the same content boundary as the doc. Captions are burned into pixels, which no later filter can undo, so a share that hides Subtitles is rendered without them and the record remembers what each ladder actually burned in; if the owner turns Subtitles off afterwards, the existing ladder is withheld rather than served, and the next render replaces it.

## One API surface, one router

Every Donkey Cut API route is a framework-free handler (web-standard request in, response out) registered once in a route table (`matchCutRoute`), namespaced under `/api/cut/*` to keep it clear of Donkey's own APIs. Both surfaces dispatch through that one table: the packaged engine mounts it directly, and the Next dev server reaches it through a single optional-catch-all route (`/api/cut/[[...slug]]`). They are the same router — static-over-dynamic precedence, HEAD, and 405s behave identically, and there is nowhere for the two to drift. The hosted 404 is applied once, in that shared dispatch.

Local data belongs to the Mac user: every account that signs in on the Mac sees the same projects and library. The page still appends the signed-in account id to engine URLs because engines released before 2026-08 refuse requests without it; the current dispatch ignores it.

## The engine

The engine is a single compiled binary built from the site's `cut/` code and version-locked to the app: the app's dev run script and release packaging build and bundle it automatically (no separate step), and the app stamps its own release version into the engine's environment, so updates ride app releases. The Donkey app spawns it at launch — regardless of sign-in, since Donkey Cut is free and standalone — restarts it with backoff if it dies, and stops it on quit. The engine's lifetime is tied to the app process: the engine watches the pid that spawned it and exits when that process is gone, and at launch the app replaces an engine on the port stamped with a different version, so engine fixes always ship with the app update. An engine matching the app's version (another instance) or a developer-run "dev" engine is left alone. Its data lives in the user's Movies folder (`~/Movies/DonkeyCut`), shared by every Donkey account that signs in on the Mac, so projects and exports are visible in Finder and openable by other apps; each project's folder is named after the project and follows renames. Its logs live under the user's Logs folder.

Because a GUI-spawned process inherits a bare PATH, the engine rebuilds it: tools shipped beside the engine binary first (they version with the app), then the app's bundled tools (bundled tool always wins), then the user's login-shell PATH and common install dirs. That is how it finds the speech tool, ffmpeg, and the user's `claude` and `codex`.

## Boundary with Donkey

| Concern | Donkey | Donkey Cut |
| --- | --- | --- |
| Sign-in | Required account | Required account; local data is per-account on the Mac |
| Billing | Credits | Free; AI generation, Gemini chat, and cloud transcription spend credits |
| Storage | Database | Local disk or the browser's own storage; cloud projects use Postgres + R2 behind a per-user quota |
| Model access | Hosted routes | CLI logins; AI generation, Gemini chat, and cloud transcription use Donkey's hosted routes (signed in) |
| Distribution | The Mac app | Rides the same app; browser and cloud projects need no install |

The only shared code runs one way: Donkey Cut uses a few site UI utilities and the Donkey auth/credits helpers on its cloud surface, and the engine rides the app's process-environment helpers. Nothing in the Donkey product imports Donkey Cut. Its database models live in their own schema file (`site/prisma/Cut.prisma`) and carry plain user ids.

## The assistant's knowledge

The AI assistant knows the editor through three surfaces: the catalog — tool definitions, the skills library, and the system prompt, shared by every provider — the browser-side tool implementations that run those tools against the live editor store, and the per-turn context snapshot sent with each message. The catalog lives with the engine's AI code; the implementations and snapshot live with the editor client code. How a chat turn actually runs — providers, the tool bridge, context budgets — is its own guide: [Donkey Cut's AI Assistant](ai-assistant.md).

**Teach the assistant in the same change.** When an editor feature lands, changes, or goes away, update those surfaces with it — usually by adding, updating, or deleting the matching tools and skills, and by extending the context snapshot when the feature adds user-visible state. A feature the catalog omits is invisible to the assistant, and a stale tool or skill is worse: the assistant confidently acts on behavior that no longer exists.

**Everything the user can point at is referenceable.** Every entity the editor lets a user select or create — a clip, a keyframe, a mask, a sticker, a title, an effect, a generated asset, a library item — carries a stable id and joins the editor's one reference model. The ref is how an entity leaves its home surface: drag it onto a drop zone, copy it with ⌘C and paste it into the chat composer, or type its @handle in a prompt, and chat resolves it back to the live entity — "tighten @c2" reaches the real clip and the tools that edit it. When a feature adds a new kind of entity, wire its ref in the same change: a scope and handle among the mention candidates, copy and drag affordances where the entity renders, and tools that accept its id. An entity without a ref is invisible to chat.

## Where it lives

The editor, its handlers, and the engine entry sit under the site app's `cut/` folder; host routing, the hosted API shut-off, and the CORS grant live in the site's proxy file (`src/proxy.ts`, the Next 16 successor to middleware). The app-side supervisor lives with the Donkey runtime code, and the packaging scripts stage the engine binary into the app bundle.
